# ORBI Pay Compliance Policy Baseline

This baseline defines the minimum controls required before ORBI Pay services are treated as production-ready for regulated financial integrations.

## Developer Access

- Developers start in sandbox.
- Live access requires business details, intended use case, verified domains, callback URLs, and operator approval.
- Production permissions are scoped by capability. Access denied responses must not reveal private platform internals.
- Staff actions against developer accounts must be audited with actor, reason, target account, timestamp, and outcome.

## Credential Handling

- API keys and webhook secrets are generated by the platform and shown once.
- Secrets are encrypted at rest.
- Developers may rotate keys through approved self-service flows where enabled.
- Every rotation must create audit evidence and notify the developer through direct messaging/email.
- Lost secrets are rotated, not recovered.

## Payment Safety

- Financial actions require idempotency keys.
- Retry behavior must not create duplicate money movement.
- Hosted challenge flows must return a clear terminal status: completed, declined, expired, canceled, disputed, or failed.
- Escrow lifecycle events must notify the relevant parties and preserve the original business reference.

## Webhooks

- Webhook events must include event ID, event type, created time, environment, integration ID, and signature.
- Merchants must verify signatures before trusting payloads.
- Failed deliveries must be replayable.
- Replay actions must be audited and rate controlled.

## Data Protection

- Developers receive only the data allowed by their approved scopes.
- Customer financial data must not be exposed without consent or a valid payment purpose.
- Logs and developer-facing errors must avoid secrets, raw tokens, private keys, and unnecessary personal data.
- Audit data must be retained according to the active ORBI retention policy.

## Monitoring And Incident Response

- Security denials, abnormal traffic, failed integrations, lockouts, key rotations, webhook failures, and live access changes must be observable by operators.
- Critical incidents require escalation evidence and resolution notes.
- Developer-facing communications should be direct, plain, and actionable.

## Release Minimum

- Full release gate passing.
- Current SDKs published and installable.
- Public docs available through the Developer Portal.
- Sandbox/live separation verified.
- Operator controls for approve, suspend, revoke, rotate, message, and audit review are available.
